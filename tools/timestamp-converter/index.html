What is Unix Timestamp?

A Unix timestamp represents seconds (or milliseconds) elapsed since 00:00:00 UTC on January 1, 1970 - the Unix epoch. This simple integer system makes time calculations efficient for computers while remaining humanly convertible to any date format.

Why Timestamps Matter in Development

Database Storage

Storing timestamps as integers (from 1970-01-01) requires exactly 4 or 8 bytes regardless of the date, whereas storing full date strings consumes more space and complicates comparisons.

API Date Handling

Most modern APIs return dates as Unix timestamps because they're timezone-agnostic. A timestamp like 1716000000 means exactly the same moment whether you're in Tokyo, London, or New York.

Distributed Systems

In microservices architectures, servers in different timezones must coordinate events. Integer timestamps eliminate ambiguity - 1716000000 always means May 18, 2025 at noon UTC.

Timezone Complexity

Unix timestamps have no concept of timezones - they're always UTC. A timestamp parsed without timezone context defaults to the local system's timezone, causing bugs like "5 PM appearing as 5 AM" when servers span multiple regions.

Example of a common bug: A server in California (PDT, UTC-7) stores 1716000000. A client in London reads it and converts to local time, getting May 18 at 5:00 AM - but the server intended May 18 at noon UTC. This 7-hour discrepancy can cause missed appointments, incorrect log searches, and payment processing failures.

Real-World Applications

  • Cache busting: ?v=1716000000 ensures users get fresh assets after updates
  • API rate limiting: Track request counts per timestamp window
  • Event ordering: Sort distributed events by their timestamp arrival
  • Token expiration: JWT tokens include exp timestamp claims
  • Log rotation: Name log files by timestamp: app-2025-05-18.log

JavaScript Timestamp quirks

JavaScript's Date.now() returns milliseconds, not seconds. Multiplying by 0.001 or dividing by 1000 is a common source of bugs. Also, older systems sometimes store timestamps as 32-bit integers, which overflow after January 19, 2038 (the Year 2038 problem).
