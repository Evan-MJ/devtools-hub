1. Requirements Clarification ⬜

Goal: Define functional & non-functional requirements. Ask clarifying questions.
  • What are the core features?
  • What is the scale (users, requests/sec, data volume)?
  • What are latency/availability/consistency requirements?
  • Any specific constraints (budget, compliance, tech stack)?

2. API Design ⬜

Goal: Define the external interfaces. Use REST/GraphQL/gRPC as appropriate.
  • List key endpoints with HTTP methods, paths, request/response
  • Consider versioning, authentication, rate limiting
  • Define error response formats

3. Data Model ⬜

Goal: Define entities, relationships, and storage choices.
  • List core entities with key fields
  • Define relationships (1:1, 1:N, M:N)
  • Choose SQL vs NoSQL per entity
  • Consider indexing, partitioning, sharding strategies

4. High-Level Architecture ⬜

Goal: Draw the system topology. Identify major components and data flow.
  • Client → Load Balancer → API Gateway → Services
  • Identify: web servers, app servers, caches, queues, databases
  • Show data flow for key operations
  • Consider: CDN, DNS, SSL termination

5. Detailed Design ⬜

Goal: Deep-dive into 1-2 critical components. Address bottlenecks.
  • Pick the most complex/high-traffic component
  • Design algorithms, caching strategies, concurrency control
  • Address: hot partitions, thundering herd, cache stampede
  • Consider: circuit breakers, retries, idempotency

6. Scaling & Reliability ⬜

Goal: Address scale bottlenecks, failure modes, and operational concerns.
  • Horizontal vs vertical scaling strategies
  • Database: read replicas, sharding, partitioning
  • Cache: invalidation, eviction, warm-up
  • Queue: backpressure, dead letters, ordering
  • Observability: metrics, logs, traces, alerts
  • Disaster recovery: backups, RPO/RTO, multi-region

What makes a good system design answer?
  • Requirements: Clear functional/non-functional split, realistic scale numbers, justified constraints
  • API: RESTful conventions, proper HTTP codes, versioning, pagination, error handling
  • Data Model: Normalized vs denormalized tradeoffs, SQL/NoSQL justification, indexing strategy
  • High-Level: Clear component boundaries, data flow arrows, stateless services, async where needed
  • Detailed: Deep-dive on 1-2 critical paths, concurrency control, caching strategy, failure handling
  • Scaling: Specific bottlenecks & solutions, observability, disaster recovery, cost awareness
Common system design interview questions
  • Design a URL shortener (bit.ly) - Hashing, collision handling, analytics
  • Design a chat system (WhatsApp) - WebSockets, message ordering, push notifications
  • Design a feed/timeline (Twitter/Instagram) - Fan-out, caching, pagination
  • Design a video platform (YouTube) - Transcoding, CDN, adaptive bitrate
  • Design a ride-sharing app (Uber) - Geospatial, matching, real-time tracking
  • Design a payment system (Stripe) - Idempotency, reconciliation, compliance
  • Design a rate limiter - Token bucket, sliding window, distributed
  • Design a search engine - Inverted index, ranking, distributed crawling
Tips for succeeding in system design interviews
  • Clarify first: Spend 5-10 min on requirements. Wrong assumptions = wrong design.
  • Estimate scale: Calculate QPS, storage, bandwidth. Back-of-envelope math shows engineering rigor.
  • Draw as you go: Visual diagrams communicate faster than text. Use the text areas to sketch ASCII diagrams.
  • Tradeoffs explicit: Every choice has pros/cons. State them: "I chose eventual consistency because..."
  • Bottlenecks honest: Identify where your design breaks. "This works to 10K QPS, beyond that we'd shard..."
  • Operate mentally: Think about deploys, rollbacks, monitoring, on-call. "We'd alert on p99 > 500ms"
